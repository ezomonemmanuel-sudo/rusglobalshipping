# Rusway architecture

## Overview

This is a Russia-origin international courier platform, not a seeded logistics demo. The app uses TanStack Start, React 19, TypeScript, Vite, Netlify Functions, Netlify Identity, and Netlify Database with Drizzle. The visual system combines a dark plum sidebar, warm orange actions, light lavender surfaces, Manrope headings, and DM Sans body text. Keep the interface responsive and preserve empty/loading/error states.

## Key directories

- `src/routes/`: Root metadata/layout, the customer workspace at `/`, public entry pages `/tracking` and `/quotes`, and role-protected `/admin`. File-based route types are generated by TanStack during the platform build.
- `src/components/Workspace.tsx`: Workspace navigation, customer and staff screens, authentication, shipment/rate/service forms, details, customs, verified tracking, and audit views.
- `src/components/WorldMap.tsx`: Code-native destination-planning SVG. It is explicitly illustrative and never represents real shipment movement.
- `src/lib/shipping.ts`: Shared country directory, Russian origin suggestions, currencies, statuses, and Zod input contracts.
- `src/lib/api.ts`: Same-origin client API requests and safe error reporting.
- `src/lib/admin.ts`: Server function used to guard `/admin`.
- `src/server/auth.ts`: Server-only live Identity verification. Do not import this into browser components.
- `netlify/functions/operations.mts`: Role/ownership-checked API, transactional writes, quote engine, tracking timeline, and audit reads.
- `netlify/functions/identity-events.mts`: Assigns the customer application role on signup.
- `db/schema.ts`, `db/index.ts`, `drizzle.config.ts`: Schema and native Netlify Database Drizzle connection.
- `netlify/database/migrations/`: Generated deployment migrations; do not edit applied migrations or snapshots.
- `src/styles.css`: Shared visual tokens, responsive layouts, motion, component styles, and accessible focus states.
- `public/favicon.svg`: Rusway brand icon. Root sharing metadata must remain product-specific; the platform supplies the sharing image.

## Security and domain invariants

Every protected API request must independently validate the session and application roles server-side. Live Identity `/user` verification is authoritative; neither editable profile metadata, client UI state, account-level role strings, nor decoded JWT claims grant privileges. Identity failure must deny access. Never add public role-assignment or bootstrap-admin APIs. Use `@netlify/identity`, never deprecated Identity clients.

Customer queries must constrain `owner_id` in SQL, including tracking lookups by number and detail lookups by UUID. Customers never receive internal handler notes, customs notes/reference fields, or operational audit records. Handler/admin roles can modify shipments and append verified events; only admin configures rates and services. Keep browser mutations same-origin and JSON-only; bearer-authenticated integrations remain subject to exactly the same server-side authorization.

Every operational mutation must insert an audit record in the same database transaction. Serialize shipment changes with a row lock. Current status/location derive from the latest actual event timestamp, not insertion order. Tracking and audit history are append-only through the app. Do not write secrets or authentication material into the database audit payload, application logs, repository, or results summary.

The origin country is always `RU`. Suggested cities are conveniences, not a closed list. Free-text Russian origin cities are allowed, and operations is responsible for validating real locations. The country directory does not imply route availability. A configured enabled service and a matching enabled route are required to create a shipment. Never seed real-looking shipments, scans, operational counts, customs releases, approvals, partners, or pricing. Customs information changes only through authorized operational actions.

Quotes are estimates, never carrier-confirmed prices. Currency-specific rates avoid fabricated conversion. Pricing uses per-package dimensions/weight and a configured volumetric divisor. An absent rate produces a useful unavailability error, not a placeholder price. Destination-specific, origin-specific, and newest rates have descending precedence.

All durable application data belongs in Netlify Database. React state is transient UI state only. Use Netlify Blobs only if adding actual file storage later. No local JSON persistence, in-memory records, or external database services.

## Conventions and deployment

Use descriptive identifiers, type-only imports, PascalCase components, and server import paths with `.js` extensions in database/functions modules. All API inputs require Zod validation. Return safe errors with request IDs; never return raw database or provider errors. Keep Netlify Function files in `.mts` format and preserve the configured custom API paths.

After schema changes, inspect `netlify db status` and generate a named Drizzle migration into `netlify/database/migrations`. Keep the Netlify adapter-compatible Drizzle versions. The platform handles build, provisioning, migration application, and deployment. Identity activation uses the relevant skill’s enable script. Initial staff assignment happens outside the customer application through an authorized Identity administrator.

Do not run build/dev/test/type-check commands in this environment; the pipeline validates builds automatically. Inspect changed source files instead. Never look inside `.git`, create commits, or print environment variable values. Refer to `README.md` for local developer instructions, operational setup, deployment checks, and backup-policy verification. Production backups and live runtime access checks must not be claimed verified without platform evidence.
